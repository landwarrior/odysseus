# Odysseus 再設計（認識合わせ）

この文書は実装の合意内容です。第12節の方針で進めています。

## 1. 何を作り直すか

Odysseus は、案件に人を割り当て、予定工数・予定原価と実績工数・実績原価を突き合わせる人材予実管理です。利用者は、管理者（案件と人の計画を持つ人）と、自分の作業時間を入れるメンバーです。

旧実装は Laravel（PHP）と MariaDB で、起動手順は Chef に依存していました。PHP と Laravel の版が古く、いまは起動できません。PHP 一式と `chef-repo` は引き継がず、捨てます。画面の言葉と業務の骨格だけを参考にします。

今回の到達点は次のとおりです。

- 利用者の PC に PHP やデータベース製品を入れなくても、実行ファイルだけで起動できる。
- 初期のデータベースは SQLite の1ファイル。
- 同じプログラムを、あとから Docker コンテナとしても動かせる。
- 接続先を設定で SQLite から別製品（想定は PostgreSQL）へ切り替えられる。
- 製品固有の SQL や型に依存する処理を、アプリの中に散らさない。

ローカル起動は「その PC のブラウザから使う」意味です。デスクトップ専用の画面にはしません。Docker でも同じ HTTP の画面がそのまま動きます。

## 2. 旧システムから読む業務

実装されていた画面は次です。

| 画面 | 誰が使う | 内容 |
| --- | --- | --- |
| ログイン、パスワード変更 | 全員 | 人材マスタがユーザーを兼ねる |
| ホーム | 全員 | 管理者には未完了案件の一覧（受注金額、人件費、終了日、予定工数、実績工数） |
| プロジェクト | 管理者 | 番号、名称、受注金額、期間。工程ごとの期間・人日・予算 |
| 人材割当 | 管理者 | 工程の中で、役割（PG / SE / PL / PM）ごとに人を選ぶ |
| 人材 | 管理者 | コード、姓、名、管理者フラグ、備考。役割ごとの時間単価と適用開始日。初期パスワードは `12345678`。一覧の氏名は姓と名を並べたフルネーム |
| 実績登録 | 割当された本人（管理者は他人分も可） | 案件ごとに、日とタスク（無ければ工程）へ時間を入れる |
| 予実確認 | （メニューはコメントアウト） | 画面は空 |

マスタとして役割と工程が初期投入されていました。

- 役割: PG、SE、PL、PM
- 工程: 提案、要件定義、基本設計、詳細設計、製造、単体テスト、結合テスト、シナリオテスト

テーブルだけあり、画面がなかったものは協力会社、部署、部署と人の紐づけです。工程マスタの `role_id` も未使用です。プロジェクトの完了フラグはホームの抽出には使われていますが、画面から変更できません。

ホームの計算は次の意味でした。

- 人件費 = 実績時間 × その人・その役割の単価
- 予定工数 = 工程明細の人日の合計
- 実績工数 = 実績時間 ÷ 8（小数第1位）

## 3. 引き継がない動き

次は不具合か未完成なので、同じ仕様にはしません。

- 単価の取り方が「その日以前で最安の単価」になっている。適用すべきは「その日以前でいちばん新しい適用開始日の単価」です。
- 割当は「誰がどの工程にいるか」だけで、その人の予定時間も期間も持てない。予実の「予」が工程の人日と予算金額だけになり、人の過不足が見えない。
- プロジェクトを消しても実績が残る。完了と削除が分かれていない。
- 予実確認画面が空で、工程別・人別の差が見えない。
- 予算金額（`pre_cost`）を保存しているのに、ホームは受注金額と実績人件費しか出さない。
- SQL が MariaDB の書き方と文字列連結になっている。
- 協力会社・部署は器だけで、運用できない。
- 初期パスワードが固定で、変更せずに使い続けられる。

旧データの移行機能は作りません。起動できない状態の資材であり、新しいスキーマへ写す対象のデータはこのリポジトリにありません。

## 4. 新しい機能

工数の正は分（整数）です。金額は円の整数です。1人日は 8 時間（480 分）とし、この時間数は設定で変えられるようにします。見積とスケジュールの割当は画面では人日（0.1 刻み）で入出力し、保存時もその刻みの分数に揃えます。差分も表示上の人日同士で計算し、四捨五入の端数で ±0.1 ずれないようにします。実績入力は時間表示です。

### 4.1 最初の版で入れるもの

認証

- ログイン、ログアウト、自分のパスワード変更。
- 初期管理者を起動時に1人作る。パスワードは初回ログインで変更する。
- 人材を追加したときの初期パスワードは、管理者が指定する。固定値は置かない。

マスタ（管理者）

- 人材。コード、姓、名、管理者かどうか、備考、在籍（有効 / 無効）。一覧では姓と名を空白でつないだフルネームを出す。実績が付いた人は削除せず無効にする。
- 役割。初期値は PG / SE / PL / PM。名前の追加・変更・並び・無効化ができる。
- 工程。初期値は旧システムの8工程。追加・変更・並び・無効化ができる。
- 単価。人材 × 役割 × 適用開始日。円/時（請負）と円/月（準委任）。どちらか一方以上。0 円も可（未入力は未設定）。同じ組み合わせの日付は1件。

プロジェクト（管理者）

- プロジェクト番号、名称、受注金額、開始日、終了日、状態（計画中 / 進行中 / 完了）。
- 工程明細。工程、開始日、終了日、予定工数（人日。タスク合計）、予算金額。1案件に同じ工程は1回。
- タスク。工程明細の細分化。名前、備考、見積工数（人日）、工程内の並び。タスクがある工程の予定工数はタスク合計になる。一覧の工程スケジュールの見積根拠であり、案件スケジュールでは工程の旬割当をタスクへ割り振る単位になる。備考はタスク名にマウスを乗せたときの title に出す。並びはプロジェクト編集で矢印により入れ替える。
- スケジュール表（プロジェクト一覧）。案件×工程の行で旬割当を直接編集する（schedule_manager と同じ使い方）。見積工数・割当済・差分、月×旬。差分 = 見積 − 工程の旬割当合計。工程に開始日・終了日があればその期間の旬に背景色を付ける。表の幅・固定列・スクロールは schedule_manager に揃える。
- 案件スケジュール。一覧で決めた工程の旬割当を、タスク行へ割り振る。工程ごとに「残工数」行（工程割当 − タスク合計）を置き、0 なら割当完了、マイナスは赤。開始〜終了の期間と工数割当の両方で背景色を付ける。
- 一覧の表フッタは旬ごとの営業日・キャパ・割当合計（工程の旬割当）。キャパ = その旬にアサイン期間が重なる人材のユニーク人数 × 営業日（人日）。同じ人は複数工程・案件でも 1 人。開始日時点の単価が 0 円のアサイン（OJT など）はキャパに含めない。割当合計がキャパの 80% 以上で黄、キャパ以上で赤。営業日は土日と祝日・休業日を除く。案件スケジュールにフッタは置かない。
- 人材アサイン。人材を選び、担当する工程・役割・単価の種類（請負＝円/時 / 準委任＝円/月）・開始日・終了日を付ける。1人に複数工程をまとめて割り当てられる。予定工数は持たない（見積は工程・タスク、稼働の枠はアサイン期間）。同じ工程に同じ人は1役割だけ。選べる人は、アサイン開始日時点でその役割の単価（時間または月間）がある有効な人材。時間と月間の両方があるときは、案件の契約に合わせてアサインごとに選ぶ。画面は人材ごとに既存アサインをまとめて出す。

実績

- メンバーは、自分がアサインされている完了前の案件だけが一覧に出る。
- 管理者は、アサインがある完了前の案件を開き、人材を選んで本人の代わりに実績を入れられる。
- 月を移動し、日付 × タスク（タスクが無い工程は工程単位）で時間を登録・上書きする。0 は削除と同じ。
- 入力できるのは、選んだ人のアサインにある工程とそのタスクに限る。1 日の合計は 24 時間まで。

予実（管理者）

- ホームは進行中案件の一覧。受注金額、予算合計、予定原価、実績原価、粗利見込み、予定工数、実績工数、終了日。
- 案件の詳細で、工程別・タスク別・人別の予定工数 / 実績工数、予算 / 実績原価、差分を出す。タスクは見積と実績の突き合わせ、工程は予定範囲内かを見る。
- 完了した案件はホームから外し、一覧では状態で絞れる。

### 4.2 次の版で入れるもの

最初の版の保存データだけで計算できるものと、追加の入力がいるものを分けます。

- 人の月次負荷。平日 × 基準時間をキャパシティとし、アサインの予定を期間で按分して月ごとに重ねる。100% 超を表示する。日本の祝日はまだ見ない。
- 月別の予定を手で置けるようにする。按分は表示用の仮であり、月別予定が入った月はそちらを優先する。
- 警告。予算超過、終了日を過ぎて未完了、工程に予定工数があるのにアサインがない、人の月次負荷がキャパシティを超える。
- 完成時予測。実績原価 + 残予定原価。残予定は「予定 − 実績」を下回らない範囲で見る。
- 協力会社。人は社内か協力会社所属かを持てる。集計で外注費と社内人件費を分ける。
- 部署。人は部署に所属し、部署単位の予実を見られる。
- CSV 出力（案件予実、実績明細）。
- 営業日カレンダー（祝日と、人ごとの所定時間）。
- プロジェクト責任者。管理者でなくても、担当案件の予実とアサインを編集できる。実績入力は従来どおり本人。

### 4.3 今回の対象外

請求、会計システム連携、メール送信、出退勤、評価、承認フロー、旧データの取り込み、多言語です。予実確認が安定してから別途判断します。

## 5. 計算ルール

単価の選択:

- ある作業日・ある人・ある役割について、適用開始日がその作業日以前の単価のうち、適用開始日が最も新しいものを使う。
- 該当がなければ原価は計算せず、未設定として画面に出す。0 円にはしない。

実績原価:

- アサインの単価種別が準委任のとき、`開始日〜min(終了日, 基準日)` に掛かる暦月数 × アサイン開始日時点の月間単価。基準日は画面表示時点の日付。工数実績は集計するが金額には使わない。月間単価が無ければ実績原価は未確定。
- 請負のとき、明細ごとに `金額 = 実績分 × 時間単価 ÷ 60`。円未満は四捨五入。時間単価が無い明細は未設定として金額に入れない。
- 案件の実績原価はその合計。役割は実績行が属するアサインの役割。

予定原価:

- アサインの単価種別が準委任なら `アサイン期間に掛かる暦月数 × 月間単価`。請負なら予定原価 0（枠は工程予算）。
- 単価をあとから変えても、既に保存した予定原価は自動では書き換えない。詳細画面から「現在の単価で予定を再計算」を明示したときだけ更新する。
- 工程の予算金額は手入力の枠です。予定原価（単価から計算）とは別に持ち、両方を並べます。予算を空にした場合、その工程の予算は予定原価の合計を表示上の予算とします。

工数の予実:

- 予定は工程・タスクの見積（とスケジュールの旬割当）。見積と旬割当は画面では人日、保存は分（0.1 人日刻みに揃える）。実績は実績分の合計で、入力画面は時間表示。実績原価はアサインの単価種別に従う。

粗利見込み:

- `受注金額 − 実績原価 − 残予定原価`。残予定原価は、アサイン予定原価のうち未消化分（予定原価 − そのアサインの実績原価。マイナスなら 0）。

この規則は実装時にテストで固定します。

## 6. 画面の流れ

```text
ログイン
  └ ホーム
       ├ 実績登録（自分の案件 → 月の時間入力。管理者は他人分も可）
       └ 管理者
            ├ プロジェクト一覧（工程スケジュール）→ 案件スケジュール（タスク割当）→ 編集（工程・タスク）→ アサイン → 予実詳細
            ├ 人材一覧 → 編集（単価履歴）
            ├ 役割
            ├ 工程
            └ 祝日・休業日
```

ブラウザは利用者が普段使っているもので足ります。実行ファイルはローカルに待受を開き、起動時にその URL をブラウザで開きます。

## 7. データの形

主キーはアプリが採番する文字列（ULID）です。データベースの自動採番（SQLite の `AUTOINCREMENT`、PostgreSQL の `SERIAL` / `IDENTITY`）は使いません。人が覚える番号（プロジェクト番号、人材コード）は一意制約のある業務キーで、主キーにはしません。番号をあとから変えても、実績との結び付きが切れないようにするためです。

日付は `YYYY-MM-DD` の文字列、時刻は UTC の RFC3339 文字列です。真偽値は 0 と 1 の整数です。外部キーは両方の製品で宣言します。

| テーブル | 主な項目 | 一意 |
| --- | --- | --- |
| person | コード、姓（name）、名（name_kana）、パスワードハッシュ、管理者、有効、備考 | コード |
| role | 名前、並び、有効 | 名前 |
| process | 名前、並び、有効、背景色 | 名前 |
| person_rate | 人材、役割、適用開始日、円/時 | 人材 + 役割 + 適用開始日 |
| project | 番号、名称、受注金額、開始日、終了日、状態 | 番号 |
| project_process | プロジェクト、工程、開始日、終了日、予定分、予算円 | プロジェクト + 工程 |
| project_task | プロジェクト工程、名前、備考、並び、予定分 | — |
| process_allocation | プロジェクト工程、年月、旬（1〜3）、予定分 | プロジェクト工程 + 年月 + 旬 |
| task_allocation | タスク、年月、旬（1〜3）、予定分 | タスク + 年月 + 旬 |
| holiday | 日付、名称 | 日付 |
| assignment | プロジェクト工程、人材、役割、開始日、終了日、単価種別、予定原価円 | プロジェクト工程 + 人材 |
| time_entry | アサイン、タスク（任意）、作業日、分 | アサイン + 作業日 + タスク（タスク無しはアサイン + 作業日） |
| app_user_secret | 初期管理者の初回パスワード変更済みか、などセッション以外の認証状態は person に持たせる | — |

`time_entry` はアサインにぶら下げ、タスクがあるときは `task_id` も持ちます。役割はアサイン側に1つなので、単価を決める材料が実績のたびに揺れません。タスク無しの行は移行前や、タスク未分割の工程向けです。

協力会社と部署のテーブルは、画面を作る版でマイグレーション追加します。使わない表は最初から置きません。

## 8. 起動と配置

提案する実装言語は Go です。理由は、実行環境を同梱した1ファイルの実行ファイルを作れ、SQLite を C コンパイラなしで組み込め、同じバイナリを Linux コンテナに置けることです。画面はサーバが返す HTML とし、利用者の PC に Node.js やブラウザ以外のランタイムは要りません。

ローカル:

- Windows では `odysseus.exe` を起動する。
- 待受の既定は `127.0.0.1` の空いているポート。同一 PC のブラウザからのみ届く。起動のたびに番号が変わり、開く URL は起動画面に出る。
- データベースファイルの既定は、実行ファイルと同じ場所の `data/odysseus.db`。
- 初回起動でテーブル作成と初期データ（管理者、役割、工程）を行う。2回目以降は未適用の変更だけを当てる。

設定は環境変数です。Docker でもローカルでも同じ名前を使います。

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `ODYSSEUS_HTTP_ADDR` | `127.0.0.1:0`（空いているポート） | 待受。固定したいときだけ指定する。コンテナでは `0.0.0.0:8080` など |
| `ODYSSEUS_DB_DRIVER` | `sqlite` | `sqlite` または `postgres` |
| `ODYSSEUS_DB_DSN` | `data/odysseus.db`（実行ファイル基準） | 接続文字列 |
| `ODYSSEUS_DATA_DIR` | 実行ファイル横の `data` | SQLite ファイルとログの置き場 |
| `ODYSSEUS_OPEN_BROWSER` | ローカルは開く、`0` で開かない | コンテナでは `0` |
| `ODYSSEUS_STANDARD_MINUTES` | `480` | 1人日の分数 |

Docker は後の版で、同じバイナリをイメージにコピーします。SQLite のままならデータ用ボリュームを `ODYSSEUS_DATA_DIR` にマウントします。PostgreSQL にするならドライバと DSN だけを変えます。アプリの分岐はそこまでに留めます。

開発者のマシンには Go が要ります。配布物を使う人には要りません。

## 9. データベースを差し替える境界

SQL はリポジトリ（案件、人材、実績、予実集計）の中だけに書きます。画面や計算ルールは、ドライバ名を知りません。

両方で同じ書き方に揃えるもの:

- プレースホルダ付きの問い合わせだけを使う。値の埋め込みはしない。プレースホルダの記号差（`?` と `$1`）はドライバ境界の1箇所で吸収する。
- 日付・時刻・真偽値・金額・工数は、第7節の置き方に固定する。
- 条件付きの関数は使わない。NULL の置き換えが必要なら `COALESCE` のみ。
- ページングは `LIMIT` / `OFFSET`。
- 登録と更新は、主キーが分かっている通常の `INSERT` と `UPDATE`。製品で構文が割れる upsert は使わない。
- マイグレーションは `internal/db/sql/` の番号付き SQL を1系列にする。現状の新規起動は `001_init.sql` に現行スキーマを集約している。どうしても文が割れるときだけ、ドライバごとの断片を Go 側のマイグレーション処理に隔離し、問い合わせ本文には混ぜない。

テストは SQLite で毎回回します。PostgreSQL 用の DSN があるとき、同じテストを PostgreSQL に対しても回せる形にします。切替の確認は「テストが両方で通ること」を条件にします。

## 11. 実装に入るときの廃棄

合意後の実装でリポジトリから外したものは `myapp/`（Laravel 一式）、`chef-repo/`、`initial.sql`、`provisioning.sh`、`fileput.sh` です。新しいプログラムはリポジトリ直下にあります。

## 12. 合意したい点

次がこのままでよければ、実装に入ります。変えたい箇所だけ指定してもらえれば、文書を直してから着手します。

1. 実装言語は Go、画面は実行ファイルが配信する HTML、配布物は単一の実行ファイル。
2. 最初のデータベースは SQLite。差し替え先の第一候補は PostgreSQL。主キーはアプリ採番の ULID。
3. 工数の正は分、金額は円、1人日は 8 時間。アサインの単価種別で請負／準委任を分ける。請負の実績原価は作業日時点の最新時間単価。準委任の実績原価はアサイン開始日の月間単価と基準日までの暦月。予定原価はアサイン開始日の単価で、明示しない限り再計算しない。
4. 最初の版の機能範囲は第4.1節（認証、マスタ、案件、工程予算、人ごとの予定工数つきアサイン、日次実績、案件予実）。月次負荷・協力会社・部署・CSV・Docker は次の版。
5. 旧データ移行はしない。PHP と Chef の資材は実装開始時に削除する。
6. 待受の既定は自分の PC だけ（`127.0.0.1`）。同じ LAN の他 PC からは、設定で待受を開いたときだけ使う。

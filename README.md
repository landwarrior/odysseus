# Odysseus

人材の予定工数・予定原価と、実績工数・実績原価を突き合わせるシステムです。実行ファイルを起動すると、その PC のブラウザから使えます。データベースの初期値は SQLite です。

利用者は次の役割を組み合わせます。

- **管理者** … 全案件とマスタ（人材・役割・工程・単価・祝日）を扱う。人材に「責任者」権限を付け、案件ごとの責任者を任命できる
- **責任者（人材フラグ）** … 案件の新規作成ができる。作成した案件には自分が責任者として入る。案件編集の責任者候補にも載る
- **案件の責任者（案件ごとの任命）** … その案件について、管理者と同等に編集・アサイン・予実・スケジュール割当・実績代行ができる（マスタは不可）
- **メンバー** … スケジュールの閲覧と、自分に割り当てられた案件への日次実績入力

金額の単位は円、工数の単位は分です。見積とスケジュール割当は画面では人日（0.1 刻み）、実績入力は時間表示です。1人日は 8 時間（480 分）です。

## できること

### 認証

- ログイン、ログアウト
- 自分のパスワード変更
- 初回起動時に管理者 `admin` を1人作成。初期パスワードは起動ログと `data/initial-admin.txt` に出る。ログイン後に変更するとそのファイルは消える
- 人材に設定するパスワードは仮パスワード（8 文字以上）。本人はログイン後に変更が必須

### ホーム

- 管理者 … 状態が進行中の案件をすべて一覧。受注金額、予算合計、予定原価、実績原価、粗利見込み、予定工数、実績工数、開始・終了、編集／アサイン／予実への導線
- 責任者 … 担当の進行中案件を同じ予実一覧で表示し、新規作成できる。自分のアサイン案件も併記
- メンバー … 自分がアサインされている案件への実績入力への導線と、スケジュール閲覧への案内

### マスタ（管理者）

- **人材** … コード、姓、名、管理者／責任者フラグ、備考、有効／無効。一覧の氏名は姓と名を並べたフルネーム。役割は、表示日時点で有効な最新の単価の役割（同じ適用開始日なら単価が最も高いもの）
- **単価** … 人材 × 役割 × 適用開始日。円／時（請負向け）と円／月（準委任向け）。どちらか一方以上。0 円も可（未入力は未設定）。同じ組み合わせの日付は1件
- **役割** … 初期値は PG / SE / PL / PM。追加、名前の変更、有効／無効、並び替え
- **工程** … 初期の工程マスタあり。追加、名前の変更、有効／無効、並び替え

### プロジェクト

- **スケジュール（全員）** … 一覧で工程の旬割当とキャパを確認。案件スケジュールでタスクへの割り振りを確認。「実績」表示も可。工数セルの入力・保存は管理者、またはその案件の責任者
- **案件の作成（管理者または責任者権限）** … 番号、名称、受注金額、開始日、終了日、状態、責任者。工程明細は工程、開始・終了、予定時間、予算。1案件に同じ工程は1回。責任者権限の作成者は、その案件の責任者に自動登録される。責任者候補は責任者権限を持つ人材だけ
- **案件の編集・削除（管理者または案件責任者）** … 担当案件を編集・削除できる。削除はプロジェクト番号の確認入力が必要（工程・アサイン・実績も消える）。責任者の任命は責任者権限を持つ人材から選ぶ
- **人材アサイン（管理者または責任者）** … 人材を選び、担当工程・役割・単価の種類（請負／準委任）・期間を付ける。複数工程を一度に割り当て可能。予定時間は入れない。同じ工程に同じ人は1役割だけ。選べるのは、開始日時点でその役割の単価（時間または月間）がある有効な人材。両方あるときはアサインごとに選ぶ。準委任は暦月数×月間単価（実績は今日までの月）、請負は工程予算と時間単価×実績工数
- 一覧は状態で絞り込み可能

### 予実（管理者または責任者）

- 案件ごとの予実画面 … 工程別・人材別の予定／実績工数、予算／予定原価／実績原価、差分
- 準委任の原価 … 人×月の月額を1回だけ計上し、受注金額がある参画案件へ受注金額比で按分（工程には分けない）
- 粗利見込み … 受注金額 − 実績原価 − 残予定原価
- 予定原価の再計算（請負の保存額を現在の単価でやり直す。準委任は按分のため 0 のまま）。単価が無いアサインは更新しない

### 実績

- 日付を選ぶと、アサイン中の完了前案件がプロジェクト → 工程 → タスクで並ぶ
- 1 画面でその日の実績をまとめて登録・上書き。空欄と 0 は削除と同じ
- 入力できるのは各アサインの期間内。1 日の合計は 24 時間まで
- 管理者は完了前案件のアサイン人材を選んで代行入力できる。責任者は担当案件のアサイン人材について代行できる

### 画面まわり

- ライト／ダークのテーマ切替（利用者ごとにデータベースへ保存。待受ポートが変わっても維持される）
- 狭い画面ではハンバーガーメニューとユーザーアイコンのメニュー

## 使い方の流れ（管理者）

案件の工数計画は、次の順を想定しています。

1. **プロジェクト編集** … 工程とタスクを登録し、見積工数（人日）を入れる
2. **人材アサイン** … 人材を選び、担当する工程・役割・期間を入れる（複数工程を一度に可。予定時間はここでは考えない）。ここでの期間が、スケジュールの工程キャパとフッタの全体キャパ（旬に重なるユニーク人数 × 営業日）の根拠になる。単価 0 円（OJT）のアサインはキャパに含めない
3. **スケジュール** … 一覧で工程の旬に工数を入れて全案件の計画を立て、セル左上の工程キャパ（その工程のアサイン人数）とフッタの全体キャパと照合する。案件スケジュールでは、その工程割当をタスクへ割り振る。80% 以上で黄、以上で赤。「実績」ボタンでメンバ入力の実績工数と見積を突き合わせて表示できる（登録は実績画面）
4. **工程の開始・終了（任意）** … プロジェクト編集で工程の期間を入れると、スケジュール表に帯（背景色）が付く。見積や自社アサインが無く、他社担当の工程を期間だけ把握したいときにも使う

工程の開始・終了はアサインの前提ではありません。先に人を置き、あとから工程の帯を付けても構いません。人材の単価は請負なら円／時、準委任なら円／月を登録します。予実の確認や実績入力は、アサインと実績が揃ったあとに行います。

## 起動

開発マシンで実行ファイルを作ります。

```powershell
go build -trimpath -ldflags "-s -w" -o odysseus.exe ./cmd/odysseus
.\odysseus.exe
```

起動した画面は開いたままにします。止めるときは Ctrl+C です。ポートは起動のたびに空いている番号を使い、ブラウザはその URL を開きます。実際のアドレスは起動ログに出ます。データは実行ファイルと同じ場所の `data` フォルダにできます。

CSS と HTML は実行ファイルに埋め込まれるため、画面を変えたらビルドし直してください。開発中の素早い確認は次の「開発用の起動」を使います。

## 開発用の起動

画面や処理を直しながら、ブラウザですぐ確認したいときです。初回だけ `air` を入れます。

```powershell
go install github.com/air-verse/air@latest
```

リポジトリの根で次を実行します。

```powershell
air
```

`.env.air` を読み、待受を `http://127.0.0.1:8080` に固定します。ブラウザでその URL を開いておきます。起動ログに「開発モード」と出れば設定が効いています。

- **HTML / CSS / JS** … ファイルを保存したあと、ブラウザを再読み込みするだけで反映されます（`ODYSSEUS_DEV=1`）
- **Go** … 保存すると `air` がビルドし直し、サーバを再起動します（数秒）

止めるときは Ctrl+C です。配布用の実行ファイルは、これまでどおり埋め込みのままです。

## 設定

Docker で動かすときも、同じ環境変数を使います。

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `ODYSSEUS_HTTP_ADDR` | `127.0.0.1:0`（空いているポート） | 待受。固定したいときだけ指定する。コンテナでは `0.0.0.0:8080` など |
| `ODYSSEUS_DB_DRIVER` | `sqlite` | `sqlite` または `postgres` |
| `ODYSSEUS_DB_DSN` | `data/odysseus.db` | 接続文字列。PostgreSQL では必須 |
| `ODYSSEUS_DATA_DIR` | 実行ファイル横の `data` | SQLite とセッション鍵の置き場 |
| `ODYSSEUS_OPEN_BROWSER` | `1` | `0` でブラウザを開かない |
| `ODYSSEUS_STANDARD_MINUTES` | `480` | 1人日の分数 |
| `ODYSSEUS_DEV` | （オフ） | `1` で HTML/CSS を埋め込みではなくディスクから都度読む。開発用 |

PostgreSQL は接続先を変えるだけで使えます。SQL は共通で、プレースホルダの違いだけを接続層で吸収しています。

## エンタープライズ／本番での注意

既定は「その PC のブラウザから HTTP で使う」想定です。社内サーバやインターネット向けに載せるときは、次を別途整えてください。アプリ本体には本番用のスイッチはまだありません。

### 初期管理者パスワードの扱い

初回起動だけ、初期パスワードを起動ログと `data/initial-admin.txt` に平文で出します（Code scanning の clear-text-logging 指摘の対象）。ローカル導入の便宜用で、本番では次のように扱います。

1. 起動直後に `admin` でログインし、パスワードを変更する（変更すると `initial-admin.txt` は消える）
2. 起動ログやバックアップにパスワードが残らないよう、ログの保管先と `data` ディレクトリの権限を制限する
3. 共有のログ基盤へ stdout を流す場合は、初回起動の行を取り込まない／マスキングする

例（Linux でデータ置き場を管理者だけに読む）:

```bash
mkdir -p /var/lib/odysseus
chmod 700 /var/lib/odysseus
export ODYSSEUS_DATA_DIR=/var/lib/odysseus
export ODYSSEUS_OPEN_BROWSER=0
./odysseus
# 起動ログの初期パスワードでログイン → すぐパスワード変更
# 変更後、initial-admin.txt が消えていることを確認
ls /var/lib/odysseus
```

人材に渡す仮パスワードも画面・口頭・別チャネルで一度だけ伝え、本人に初回変更させる運用にしてください。

### Cookie の Secure 属性

セッション（`odysseus_session`）と通知（`odysseus_flash`）の Cookie は `HttpOnly` と `SameSite=Lax` を付けますが、既定が HTTP のため `Secure` は付けていません（Code scanning の cookie-secure-not-set 指摘の対象）。HTTPS で公開するときは、TLS を終端するリバースプロキシの手前に置き、プロキシ側で `Secure` を付与する例があります。

例（nginx で TLS 終端し、下流の Set-Cookie に Secure を足す）:

```nginx
server {
    listen 443 ssl;
    server_name odysseus.example.internal;
    # ssl_certificate / ssl_certificate_key は環境に合わせて設定

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_cookie_flags ~ secure samesite=lax httponly;
    }
}
```

Odysseus 側の待受例:

```powershell
$env:ODYSSEUS_HTTP_ADDR = "127.0.0.1:8080"
$env:ODYSSEUS_OPEN_BROWSER = "0"
.\odysseus.exe
```

待受はループバックだけにし、外からは必ず HTTPS のプロキシ経由にしてください。アプリ単体で HTTPS を終端する機能はありません。

## テスト

```powershell
go test ./...
```

PostgreSQL でも同じマイグレーションを確認する場合は、空のデータベースを指す `ODYSSEUS_TEST_POSTGRES_DSN` を置いてからテストします。無ければその確認は飛ばします。
